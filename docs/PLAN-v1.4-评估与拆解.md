# 对《24H-OS 设计与落地方案 v1.4.0》的评估与拆解

> 评估人：负责实现的工程侧（我）；评估日期 2026-09-17。
> 评估方式：逐章对照**本仓现有代码与实测结果**（不是纸面互评），并给出可执行的分期与分工建议。

## 一、结论（先看这三句）

1. **方向可以落地，但不是"照这份清单一次做完"**：方案是三个参考产品的**功能并集**（§二 三行全写"✅ 全部吸收"），
   而并集规模远超 Phase 1–3 自估的 11–16 周。按本仓这几天的实测速度折算，**单人全职做 Phase 1–3 现实是 6–9 个月**。
2. **已经落地了约四分之一，而且是最难"从 0 到能用"的那部分**：Electron 壳、核心进程监护、流式对话、
   契约版本对齐、会话数据权威性（方案决策十五）**已经是本仓的现状**，运行时随包 + 资产化 + 分发源下载 + 回退也跑通了。
3. **今天不需要组队；该组队的是"插件系统 + 多连接"那两块**。现在瓶颈不是"打字的人不够"，而是
   ① 产品范围要砍 ② Windows 真机验收在我这边做不到 ③ 设计与安全评审需要人。这三件都不是"多招几个工程师"能解决的。

## 二、逐章对照：方案要什么 vs 本仓现在有什么

| 方案要求 | 现状 | 证据（本仓） |
|---|---|---|
| Electron 壳 + 进程监护（§3.1/§8） | ✅ 有；**孤儿回收今天补齐** | `electron/main.js`、`electron/orphan-sweep.mjs`；`scripts/dev/orphan-e2e.sh` 实测：父进程活着不动、变孤儿后回收 |
| Daemon 与壳分离 | 🟡 部分：核心是独立进程（`hermes serve`）但**没有独立 Daemon 层** | `electron/runtime.js`；方案里的 Daemon（任务镜像/连接注册表）尚不存在 |
| 首次启动向导（§5.11/§7.27，6 步必过） | 🟡 部分：未配模型有引导横幅 + 设置分节；**没有"必过向导"** | `src/renderer.js`（setup.ready → 横幅 → 去设置） |

**统计**：方案 17 章里，**已具备 6 项、部分具备 3 项、完全没有 8 类**。

## 三、规模与风险（说人话）

- **Phase 1**（方案自估 4–6 周）：Monorepo + Daemon + 首启向导 + 版本迁移 + 连接注册表雏形 + 事件分片 + 凭证钥匙串。
  → 现实：**6–10 周**（其中 Daemon 与连接注册表是从零起一层运行时结构，不是加功能）。
- **Phase 2**（插件系统）：**这是全案最重的一块**。沙箱、签名、权限仲裁、热加载回滚、事件来源校验、动态代码拦截——
  任何一条做不好都是安全事件；且需要"人来评审"，不是"多写代码"。现实：**2–4 个月**，且必须有人做安全评审。
- **Phase 3**（体验完善，含移动端 PWA、Tailscale、渠道桥接、多端同步）：**2–4 个月**，且渠道桥接涉及第三方平台资质（微信/钉钉/飞书）。
- **Phase 4**（商业化：SSO、插件市场、审计、Docker）：**持续**，其中"插件市场 + 签名校验"依赖 Phase 2 先跑通。

**三个真实瓶颈（都不是"代码写得慢"）**：
1. **产品范围**：把"能吸收"当成"该吸收"。三个参考产品的并集里，**至少一半是给专业用户/企业用的**（Kanban、A2A、审计、SSO、渠道桥），
   而 24H-OS 当前给人的价值是"装完就能用中文对话的个人助手"。范围不砍，Phase 2/3 会永远做不完。
2. **真机验收**：Windows 安装包、真机首启、多机/多端，这些只能在你机器/你的用户那里验；我这边只能做到"解包包内自检 + CI"。
3. **设计与安全评审**：视觉规范（方案的"底部极简/固定悬浮/级联可见"这些要人眼拍）与插件沙箱的安全边界，需要人来定。

## 四、团队建议（直接回答"我一个人还是组队"）

**结论：现在不组队；到 Phase 2 开始时再补 1–2 个人。**

| 阶段 | 谁做 | 为什么 |
|---|---|---|
| 现在 → Phase 1 收口 | **我（实现）+ 你（验收/拍板）** | 这几天的事实：从空白到"能装能跑 + CI + 分发源"，代码侧几乎全是我完成的，你在 Windows 上验收。这条分工没有卡住过 |
| Phase 1 里的"首启向导 / 草稿保护 / 并发锁" | 我 | 都是本仓现有代码的自然延伸，我能自己做断言与截图自检 |
| Phase 2（插件系统 / 多连接） | **我 + 1 名安全/后端 + 1 名 Electron/TS 熟手（可选）** | 插件沙箱与权限仲裁需要第二双眼睛；多连接的连接注册表/协议适配是纯工程量大，可以并行 |
| 设计（视觉/交互规范） | **1 名设计师（兼职即可）** | 方案的三条界面原则需要人眼拍；我按规范实现没问题，但不该由我来定"好不好看" |
| QA（真机/多机/多端回归） | **你 + 1 名测试（Phase 3 起）** | 我给你可重复的脚本与清单，但真机矩阵必须有人跑 |
| 商业（账号/额度/市场） | **你 + 我（实现）+ 1 名后端** | 门户兼容后端已验通（5/5）；从"能跑"到"能收费"要后端长期维护 |

**一句话**：如果目标是"3 个月内按这份清单全做完"，那需要 4–6 人，且仍然不现实（Phase 2 的安全评审无法并行压缩）。
如果目标是"3 个月内做出一版能卖的产品"，那**现在这套双人分工就够**，甚至能更早——只要范围砍对。

## 五、我建议的 V1 范围（砍出来的"能卖"版本）

保留（与"个人助手"直接相关）：
1. 对话闭环（已有）+ 首次启动向导（**本周做**）
2. 数据不丢类：草稿/输入保护、会话导出、孤儿回收（**已做**）、崩溃后自动恢复连接（**本周做**）
3. 模型接入：DeepSeek（已有）+ 自定义端点（已有）
4. 运行时升级链路（已有：分发源 + 下载 + 校验 + 回退）
5. 打包交付：NSIS 安装包（**等你跑 `npm run dist`**）+ 图标 + 更新检查（已有）

**明确推迟到 V2**：插件系统、多连接（KAL）、Artifact/Kanban/工作流、A2A、移动端 PWA、渠道桥接、SSO、插件市场。

理由（一句话版）：这七项里，**插件系统与多连接是"平台能力"**（面向开发者与多机用户），
而 V1 的用户是"一个人、一台机器、一个模型"——先把这条路径做到"零疑问"，再谈平台化。

## 七、需要你拍板的三件事

1. **V1 范围**：接受"先砍掉插件系统/多连接/移动端"吗？（不接受也行，但要接受周期从 3 个月变成 6–9 个月）
