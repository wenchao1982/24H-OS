# Sprint-01 · 分工与验收（对齐《24H-OS 方案 v1.4.0》）

> 基线（2026-09-17 实测）：本仓 49 个文件与 GitHub `main` 逐文件 blob sha 一致；
> `npm run smoke -- --static` **15/15**；`runtime/` 在位（379MB，core 0.21.3）。
> 方案全文：`docs/PLAN-v1.4-评估与拆解.md`（逐章对照结论）；架构与决策：`docs/PLAN.md`。

## 0. 本轮目标（一句话）

把 v1.4.0 的**两个"断点"**做到零疑问：**首启可用**（首次启动必须能走完配置）+ **输入不丢**（任何切换/关窗前保护未发送内容）。
不换架构：继续在已验证的 Electron 壳（vanilla JS + preload.cjs）上补齐，**不引入** React/TS/SQLite 重写。

**落盘约定**：草稿、滚动位置、向导完成态一律进壳侧存储（`ui-prefs.json` 扩展或同级新 store），**不引入 SQLite**——当前壳没有 DB 层，引入它等于换架构。

## 2. 本轮不做（明确推迟，避免"做一半发现载体不对"）

插件系统 / 沙箱 / 签名 / 热加载 · 多连接 KAL 与 Connection Registry · 独立 Daemon 层与任务镜像（30s 校准）·
Kanban / Artifact / 工作流审批 / A2A · 移动端 PWA / Tailscale / 渠道桥接 · 企业 SSO / 插件市场 / Docker ·
凭证钥匙串（keytar）· 审计日志 · 把壳重写成 React 19 + TS + pnpm/Turborepo。

理由：这九项里前六项依赖"连接注册表 + Daemon"这层尚不存在的新基建；末两项是**换架构**，会作废已经跑通的壳/契约/打包链路。

## 3. 审查（审查 agent，随交付滚动做）

1. **护栏类**（历史上真出过事故，必须逐条查）：`preload` 必须是 CJS 且被 `main.js` 引用；`src/` 不得出现内联 `style=`（CSP `style-src 'self'`）；壳调的 gateway 方法名与事件名必须在 `electron/contract.generated.json` 里命中。
2. **证据类**：不采信自述。每个任务给"命令 + 原始输出 + 截图路径"，能由第二个人重跑。
3. **偏差类**：核对方案里"当前架构不适用"的条目（任务权威源 / 连接注册表 / keytar / 插件沙箱），每条给一句话结论，防止后续按方案做一半才发现载体不对。

## 4. 协作约定

- 分支与推送：本机到 `github.com` 的 git 通道不通，推送一律走 `~/push-24h-os.py`（API 推送 + blob sha 回读校验），由项目经理统一执行，避免并发推远端互相覆盖。
- 每人只改自己那一摊文件：前端 `src/**`，后端 `electron/**` + `scripts/**`，审查不改代码只出结论。
- 任何"做完了"必须附一条**本次新增且通过**的断言/用例名，否则按未完成计。
